# Step 2: JS stage engine

The stage engine in JavaScript, with no runtime dependencies. It runs
unchanged in Node and, in step 3, inside a browser Web Worker on each phone.
It implements the same contract as [`reference/stage.py`](../reference/stage.py)
and is checked against the Python reference's test vectors. The matmuls run
in WebAssembly SIMD where available (every current browser and Node), and in
plain JS otherwise.

## Run

Needs Node 20+ and the outputs of step 1 (`weights/` and `testvectors/`):

```sh
.venv/bin/python reference/export.py   # if weights/ is missing
.venv/bin/python reference/check.py    # if testvectors/ is missing
cd engine && npm run check             # 16 checks on the WASM SIMD kernels, about 10 s
npm run check:js                       # the same checks on the plain JS kernels, about 50 s
```

A passing run ends with `16/16 checks passed`. After editing
`src/kernels.wat`, rebuild with `npm install && npm run build:wasm`.

## What the checks prove

| Check | Result on this laptop |
|---|---|
| h after the embedding and every layer matches Python, prompt pass | worst relative error 1.2e-6 |
| Same for 3 decode steps through the KV cache | worst relative error 6.8e-7 |
| Logits match | max abs diff 2.9e-5 |
| Greedy tokens through the 3-block split equal Python's and Hugging Face's | 40 of 40 |
| Every other split, down to one layer per stage, is **bit-identical** | yes |
| Prompt in one pass vs one token at a time is **bit-identical** | yes (NumPy only agreed to 4e-5) |
| Interleaved sessions equal each session run alone | yes |

Planted bugs that the checks catch: wrong query-to-KV head mapping, RoPE
pairing neighbouring dimensions (llama2.c's convention, not Hugging Face's),
and a KV cache that forgets earlier tokens.

## Files

| File | Role |
|---|---|
| `src/kernels.js` | The math: matmul, RMSNorm, RoPE, attention, SiLU, in plain JS |
| `src/kernels.wat` | Matmul in WebAssembly SIMD, float32 and int8 |
| `src/kernels-wasm.js` | `kernels.wat` compiled, as base64 (generated by `npm run build:wasm`) |
| `src/wasm.js` | `WasmArena`: one stage's matrices in its own wasm memory, and the calls into the kernels |
| `src/stage.js` | `Stage.load({ manifest, start, end, readFile, kernels })`, then `forward(sessionId, x, pos)` |
| `src/pipeline.js` | Stages in a chain, h passed as raw bytes; greedy `generate()` |
| `src/node-files.js` | Node-only: read weights and test vectors from disk |
| `test/check.js` | The checks |

## Using a stage

```js
import { openWeights } from "./src/node-files.js";
import { Stage } from "./src/stage.js";

const weights = await openWeights("../weights/smollm2-135m-instruct");
const first = await Stage.load({ ...weights, start: 0, end: 8 });
const second = await Stage.load({ ...weights, start: 8, end: 30 });

const h = first.forward("session-1", [1, 9690, 198], 0);              // Float32Array, 3 × 576
const logits = second.forward("session-1", h, 0, { lastOnly: true });  // Float32Array, 49152
```

In the browser, `readFile` becomes `(name) => fetch(url + name).then((r) => r.arrayBuffer())`.

## Differences from the Python reference

- Dot products accumulate in float64, which is JS's number type, and every
  stored value is float32. That's why results agree with NumPy to about 1e-6
  rather than bit for bit.
- The last stage can return logits for the last position only
  (`{ lastOnly: true }`). Generation only needs that one row, and it saves a
  49152 × 576 matmul for every other prompt token.
- The WASM matmuls sum each dot product in float32 (four 4-lane
  accumulators, lanes added in a fixed order, no fused multiply-add), so
  they are bit-identical on every machine. The plain JS ones sum in float64.
  Both match Python to about 1e-6.
- `Math.exp`, `Math.cos` and `Math.sin` in attention, RoPE and SiLU still run
  in JS and may differ in the last bit between browsers, so two phones on
  different browsers are not yet guaranteed bit-identical. Moving those into
  WASM too is what the planned hash-based verification needs.

## Speed

Whole model on one thread of this laptop, 40-token prompt then 39 tokens:

| Kernels | Prompt | Per token |
|---|---|---|
| Plain JS | 4.0 s | 130 ms |
| WASM SIMD, float32 | 0.34 s | 30 ms |
| WASM SIMD, int8 | 0.50 s | 20 ms |

Through the swarm (three phones in one Node process) that is 32 ms per token
instead of 165. Three tabs of one browser on this laptop: 54 ms per token.

Each stage keeps its matrices in its own wasm memory (an arena), so a
dropped stage frees them. wasm32 memory tops out at 4 GB per stage.
